# Persistence Guidelines

These rules decide which storage a program in this repository uses. Code review enforces them.
They are language-agnostic; for Rust, the client libraries are in [`rust.md`](rust.md) (§9).

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Choosing the storage

Pick the storage by the shape of the data:

| Data                                                            | Storage        |
|-----------------------------------------------------------------|----------------|
| Relational: records with a fixed schema, relations, queries     | **PostgreSQL** |
| Documents: self-contained, schema-less or deeply nested objects | **MongoDB**    |
| Key-value cache: short-lived values looked up by key            | **Redis**      |

- These are the preferred choices. Another product is used only when the preferred one cannot do
  the job, and the reason is written down with the project's documentation.
- Prefer one storage per program. Add a second one only when the data really has a different
  shape (for example PostgreSQL for the records and Redis for a cache in front of them).

## 2. Data conventions (every storage)

- **Dates and times are stored in UTC, without time-zone information**, unless a feature needs
  the original offset or a local time (then the reason is documented next to the field). The
  program converts to UTC before writing and treats what it reads as UTC.
- **Primary keys are UUIDs.** Natural keys (a name, a code, a callsign) are not primary keys:
  they get a unique constraint or index instead, so that they can change without touching every
  reference. Prefer time-ordered UUIDs (version 7) when the key is also used for sorting;
  otherwise random UUIDs (version 4) are fine. This applies especially to relational databases.

## 3. PostgreSQL

- The schema is defined by versioned migrations kept with the code and applied by the program
  (at startup, or by a dedicated "migrate only" action). Nobody changes the schema by hand.
- Store times as `timestamp` (without time zone) holding UTC (§2), primary keys as `uuid`
  (`DEFAULT gen_random_uuid()`, or generated by the program), and structured sub-objects that are
  never queried by their fields as `jsonb`.
- Do not rely on the order of UUIDv4 keys: sort by a time column, with the key as a tie-breaker.
- Every query that filters or sorts a large table has a supporting index, created by a migration.

## 4. MongoDB

- Every collection has a documented document shape, even though MongoDB does not enforce it.
- `_id` is a UUID (stored as BSON binary subtype 4), not an `ObjectId`; times are BSON dates (UTC).
- Indexes are created by the program at startup (idempotently) or by migrations, never by hand.

## 5. Redis

- Redis holds caches and other data that can be lost: a restart or an eviction MUST NOT lose
  information that exists nowhere else.
- Every key has an expiry (TTL), and key names have a program-specific prefix
  (`<program>:<area>:<id>`).

## 6. Connections

- The connection address is an ordinary setting of the program (command line, environment, file).
- Passwords and tokens are never written to logs or error messages.
- The program fails at startup, with a clear error, when a storage it needs is unreachable.
